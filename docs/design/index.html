01. Legacy "Doctor Clinic" (2018) Analysis

Source: ~/Doctor-Clinic/DoctorClinic/ (jar dated Dec 2017, logs to Dec 2018). Only compiled classes are present; there is no Java source except one Eclipse WindowBuilder helper. Findings come from the jar class list, the MySQL schema (Original Database/doctorclinic.sql), Jasper report templates, folder layout and the error logs. Patient photos, PDFs and the SQL dumps contain real patient data and were not opened or copied.

Migration is built only after MVP1-MVP4 work end to end (requirement IMP-002). The design below is kept ready.

02. MVP1 Architecture Overview

Scope: MVP1 from ../requirements/: a complete offline desktop app for Windows and Linux with no hosted servers. Doctors pay to our business UPI ID through a QR the app generates offline, send proof on WhatsApp, and receive a signed licence by email from our offline Vendor Licence Tool (requirements 03 section 3, design 04). The hosted backend shown in the diagrams is MVP2 (built when MVP1 revenue funds it); it is designed now so MVP1 choices do not block it. Migration is MVP5.

6. Security architecture

Diagram: key hierarchy in diagram 12-state-licence (licence) and diagram 11-seq-backup-restore (backup keys).

Concern Design
At rest Data Encryption Key (DEK, random 256-bit) encrypts clinic.db, user_content.db (SQLCipher) and files (AES-256-GCM). DEK is wrapped by a Key Encryption Key derived from the PIN (Argon2id) and also by the OS store (Windows DPAPI / Linux Secret Service). Recovery code wraps a third copy.
Backups Separate backup key from backup password (Argon2id); .hcbak = header + encrypted tar of DB snapshot and files
Network MVP1 desktop opens no listening ports and has no server to call; it only hands wa.me / mailto links to the OS and optionally reads a signed update manifest over TLS 1.2+. MVP2: licence API with certificate pinning
Packs and updates Ed25519 signatures verified before use; two embedded public keys for rotation
Backend (MVP2) Auth on every non-public endpoint, admin behind SSO + 2FA, webhook HMAC check, rate limits, KMS signing, no patient data
Code Parameterised SQL only, cargo audit/npm audit in CI, pinned dependencies, Content Security Policy in webview, Tauri capability allowlist (no shell, no arbitrary FS)
Tamper / crack protection (TAM-001..013) Layered, see section 6b

6b. Tamper-proof release build

Diagram: diagram 18-secure-release-pipeline.

No client binary is truly uncrackable, so protection is layered so that cracking is expensive and a cracked copy is still of little value:

Layer What it does Requirement
1. Single native blob Rust compiles to machine code (not decompilable like the legacy Java jar). UI assets are embedded in the exe, encrypted at build time, decrypted in memory only TAM-001
2. Hardened compile Fat LTO, stripped symbols, no debug info, devtools and debug commands compiled out, minified/mangled frontend TAM-002
3. Hidden secrets Compile-time string encryption for keys, URLs, licence messages TAM-003
4. Many licence checks Licence logic inlined at startup, new-visit/Rx/bill, background timer (MVP2: also pack open); each verifies differently TAM-004
5. Self-integrity Signed hash manifest of code sections embedded at build; randomised runtime re-hash; Authenticode self-check on Windows TAM-005, TAM-006
6. Anti-debug / anti-hook Debugger and injection detection; silently disables paid paths TAM-007
7. Targeted obfuscation Control-flow obfuscation only on hc-licence and pack-decrypt code TAM-008
8. Server-held value (MVP2) Paid packs encrypted, key only inside device-bound licence; updates, cloud, sync, SMS require server-checked licence TAM-009, LIC-031
9. Traceability Per-licence watermark and identity printed on every document (MVP1, TAM-014); server abuse detection and revocation (MVP2) TAM-010, TAM-011, TAM-014

Release pipeline (TAM-012): build on a locked CI runner -> embed and encrypt assets -> compile hardened -> obfuscate licence modules -> compute and sign code-section manifest -> inject manifest -> Authenticode/GPG sign via hardware key / HSM (MVP2: KMS) -> automated release scan (no symbols, no devtools, no plain secrets, signatures valid, Defender scan clean) -> publish. Any failed step blocks the release.

Response policy (TAM-013): tamper detection only blocks new paid actions (Read-only mode). Patient data is never deleted, encrypted or hidden, and the PC is never affected.

UX guardrails (SUX-001..012): every layer above is designed to be invisible to a genuine doctor.

Layer How it stays invisible
Encrypted embedded assets Decrypted once at startup into memory (about 20 MB, < 150 ms), counted in the 4 s cold-start budget
Obfuscation Applied only to hc-licence and pack-decrypt, never to search, scoring, DB or UI code, so hot paths keep full speed
Licence checks Run in background or piggyback on write commands (< 1 ms each); no dialogs
Self-integrity Background idle-time hashing in < 5 ms chunks; restriction needs 2 independent failures; first response is automatic Repair
Anti-debug Silent, only affects paid paths, never crashes or shows warnings
Paid pack keys (MVP2) Unwrapped once per session at first pack open (< 50 ms)
Signing EV certificate so no SmartScreen warning; per-user install, no admin, no firewall prompt
Restriction Never interrupts an ongoing visit (SUX-008); friendly message with one action button (SUX-007)

Verification: performance and usability tests run on the fully protected release build (SUX-001, acceptance flow 13).

Not used: kernel drivers / rootkit-style DRM and whole-binary packers (UPX, VMProtect) because they cause antivirus false positives and erode doctor trust.

03. Repertory Engine Design

Requirements: REP-, MM-, PACK-, CIT- in requirements/02-repertory-engine.md. Diagrams: diagram 06-er-content, diagram 08-seq-repertorise, diagram 15-pack-pipeline.

1. Components

Component Responsibility
PackRegistry Discovers content/*.hcpack, verifies signature + checksum + entitlement, attaches each pack DB read-only, exposes enabled packs
RemedyMaster Merged remedy list across packs (MM-001, PACK-008); maps pack remedy codes to global remedy ids
RubricSearch FTS5 trigram over full_path + synonym expansion + abbreviation expansion; ranking
RubricStore Rubric tree navigation, rubric detail, cross-refs; reads pack DB + user_content.db overlay
ScoringEngine Builds per-rubric remedy bitsets and grade arrays; runs analysis methods
CitationService CRUD for sources/citations/links; overlay of doctor additions
MMReader Materia Medica sections, full-text search, compare

2. Rubric search pipeline (REP-010..017)

  1. Normalise input: lowercase, strip punctuation, British/US spelling map.
  2. Expand: each word -> {word, synonyms(word, lang), abbreviation forms}; multi-word synonyms matched first ("loose motions" -> "diarrhoea").
  3. Query every enabled pack's rubric_fts with MATCH on expanded terms (AND across user words, OR within a word's expansions).
  4. Rank: score = BM25 + 3 x (all words in leaf text) + 2 x (chapter matches a chapter synonym) + 1 x log(remedy_count) - 0.5 x depth. Top 50.
  5. Return rows with full path, remedy count, top 5 remedies (precomputed column top5_json in pack).

Budget: < 100 ms per keystroke (NFR-003). Query cancelled when the next keystroke arrives.

3. Scoring engine (REP-033..036)

Data per analysis (built when a rubric is added, cached by rubric id): - present: BitSet over global remedy index (about 2,500 remedies = 40 x u64) - grade: [u8; N] sparse map for remedies present (normalised 1..3 via pack grade_scale) - doctor additions from user_rubric_remedy merged when "include my additions" is on (CIT-008), marked with a flag bitset

Algorithm (all methods share one loop):

candidates = ALL
for r in eliminative rubrics: candidates &= present[r]
for m in candidates:
    for r in active rubrics:
        g = grade[r][m]; if g == 0: continue
        cover[m] += 1
        score[m] += g * w(r) * chapterWeight(method, r.chapter)
        if method.smallBonus and r.remedy_count < T: score[m] += B
        if method == Boenninghausen: add parent rubric grades at g-1
sort by method key (score, cover, abbrev)

Complexity: 30 rubrics x 2,500 remedies = 75k operations, well under 1 ms. The 300 ms budget is for the UI.

Snapshot (REP-038): rubric list + settings + top 20 results stored in analysis.result_snapshot_json so an old analysis opens identically even after packs change.

4. Pack format (PACK-001..013)

2. Offline Pay QR (PAY-011, PAY-012)

  • Matching keys: tn/tr carry install_id; UTR is the authoritative match (some apps drop notes).
  • Fallback text with Copy buttons; payee-name check hint.

4. Licence formats

Full licence (.hclic file and certificate QR), CBOR payload + signature, base64url:

{
  "v": 1, "key_id": "k1",
  "licence_id": "L-2611-000123",
  "sku": "CLINIC_1Y",
  "holder": { "name": "DR ASHA KULKARNI", "reg_no": "12345", "council": "MCH", "email": "...", "mobile": "+91..." },
  "install_id": "HC-7K3P9",
  "issued_at": "2026-11-01", "valid_from": "2026-11-01", "valid_until": "2027-10-31",
  "entitlements": ["core"],
  "utr_hash": "sha256:..."
}

Typed key (LIC-046): 22-byte compact payload (licence_id, sku, valid_from/until as day numbers, 8-byte hash of normalised name + reg no, key_id) + 64-byte signature = 86 bytes -> 138 base32 data chars, split into 35 groups of 4 data chars + 1 check char = 175 characters shown as 35 groups of 5. Normalisation: uppercase, collapse spaces, strip "DR."/punctuation.

Verification on import and on each check site (TAM-004): signature with embedded key, valid_from <= today_guarded <= valid_until (+15 d grace), identity hash matches the locked profile.

5. Identity binding (LIC-006)

  • On first activation, doctor.name and doctor.reg_no are overwritten with licence values and marked locked; print templates read the identity only from the verified licence, not from editable settings, so editing the database does not change prints.
  • Re-import on another PC: same licence, same identity, no limit. A different doctor's licence on the same install is rejected unless the profile is reset (which starts a new clinic profile, MVP1 = one licensed doctor per install).

6. Licence states

Diagram: diagram 12-state-licence.

Unlicensed -> Trial(30d) -> Active -> Grace(15d) -> ReadOnly, Any -> Tampered (signature fail confirmed twice, treated as ReadOnly with banner and Repair). Active -> Revoked exists only from MVP2 (online refresh). ReadOnly always allows view, search, print and export.

Clock guard: state.bin stores max seen UTC time, HMAC-ed with a key derived from the DEK. If now < max_seen - 48 h, use max_seen for expiry checks (LIC-005).

9. Hosted UPI flows (MVP2, PAY-002, PAY-006)

  • One-time purchase: Razorpay Order -> Checkout with UPI Intent (mobile) or UPI QR (desktop browser) -> webhook payment.captured -> licence issued -> SMS + email with key, response code and GST invoice.
  • Subscription: Razorpay Subscription with UPI AutoPay mandate -> webhook subscription.charged each cycle extends valid_until -> desktop picks up on next online refresh, or doctor imports new response code. Pre-debit notification handled by Razorpay per RBI rules.

10. Crack resistance of the licence path (TAM)

  • hc-licence is built with control-flow obfuscation (TAM-008); its public key and messages are compile-time encrypted (TAM-003).
  • Verification is not one function call. Four independent check sites (startup, write commands, pack open, 20-60 min random timer) each re-verify the signature and derive the licence state differently, and the results feed the encryption key path of paid packs, so a patched "return true" still cannot decrypt paid content (TAM-004, TAM-009).
  • MVP1: no paid packs; sharing is deterred by identity binding (section 5, TAM-014) and forging is impossible without our signing key.
  • MVP2 paid pack key flow: server generates pack_key once per pack; for each licence it adds wrapped_key = AES-KW(KDF(licence_secret, device_fp), pack_key) to the signed licence (LIC-031). The app unwraps in memory at pack open and zeroises after use.
  • Watermark: licence_id is folded into the per-licence wrapped keys and into invisible ordering markers in paid pack exports, so a leaked pack or key traces back to the buyer (TAM-010).
  • MVP2 server signals: activation count per key, fingerprint churn, geographic spread, refresh from known cracked builds (integrity report from TAM-005) -> automatic revocation and update block (TAM-011).
